# 04｜协作、代码评审和交付流程

## 每个功能的最小闭环
问题/验收 → 复用调查 → 必要ADR → 单一责任的小PR → 主机与SDK检查 → 机测证据 → 更新能力台账 → 合并。先证明一条真实拍摄链路，不先堆所有设置页。

Issue至少说明：用户收益、非目标、现有源码候选与排除理由、受影响模块、验收条件、回退办法。PR必须区分“本机已运行”“只读源码”“需设备测试”。不存在设备证据时不能写compatible/verified。

## 分支与版本
使用main加短期feature/fix分支；不需要长期多层分支。main的标准是检查可执行、现状真实，不是所有研发能力必须已完成。pre-release使用0.x.y-dev/alpha；稳定版和探针包不共用误导标签。提交可采用 `feat: / fix: / refactor: / docs: / test:`，重点是清楚的变更和理由，不是提交名装饰。

无硬性“一次改几行”；跨模块变更仍需界面契约和迁移说明。外部来源代码保留上游版本和差异，不把上游更新夹在几何重构里。

## 评审职责
至少由另一轮独立审查检查：源图安全、结果真实性、资源释放、API10约束、许可和设备范围。个人维护场景应另行复查并记录检查范围；评审结论不能替代设备测试或作者授权。

同一任务由一名负责人修改适配器或构建脚本；其他贡献者可以开展只读调研、测试或审查。合并冲突由任务负责人解决，避免相互覆盖。贡献要求见 CONTRIBUTING.md，模块边界见 02_ARCHITECTURE.md。

## CI与供应链
已保留可选GitHub host工作流和手动Android资格工作流；Gitee尚未接入执行器，这些YAML不会作为Gitee运行证据。实际是否运行见对应远端记录，而不是看到YAML就说CI绿。actions以检索到的完整提交SHA固定，最小contents:read；禁用pull_request_target执行外部PR代码，不给PR发签名密钥，不使用continue-on-error掩盖失败。[S18]

Dependabot用于提示Actions版本更新，更新需审查兼容性后再固定新SHA。当前JDK按主版本矩阵，不代表完整分发hash锁定；正式资格阶段补齐。SHA固定的Actions仍需按对应版本人工核对安全公告，不能以Dependabot版本更新代替完整安全审计。测试脚本主动下载依赖必须另审，目前主机check不下载。

## 远程仓库配置清单（尚未执行）
按用户决定创建Gitee私有仓库（账户待确认）；确认正式包名和代码版权标注；启用main保护、必须通过的实际job名称、禁止force-push、必要review；启用适用的secret scanning/私有漏洞报告；把CODEOWNERS.example里的注释替换为真实维护者再启用。未完成这些动作不能说“分支保护已配置”。

签名发布单独人工批准；导入密钥与备份由维护者完成，不通过聊天传私钥。主机测试产物可公开，设备日志需脱敏，个人照片默认不上传。

## 发布
产品发布需要config/release-gates.json逐项证据。门禁至少包括真实SDK编译/签名、API/DEX检查、首测机型/固件、原片不变、几何/颜色、安装卸载、许可、签名管理。探针可以在有警告说明的开发渠道测试，但不能名为已支持的产品版。

每个release同时提供：源码提交、APKhash、签名证书指纹、兼容矩阵、已知限制、来源NOTICE、构建信息、回退方式。SBOM在实际依赖选定后从真实依赖生成；当前upstreams台账不是一个完整SBOM。

## 文档与完成标准

任务完成需要：验收范围明确、模块边界通过、变更对应测试和真实证据、用户文档/状态/变更记录同步、任务视图生成。详见[文档制度](DOCUMENTATION.md)。

当前托管执行见[Gitee接入](GITEE.md)。PR使用.gitee模板；未配远端CI时提交本地命令结果，不能填远端绿灯。CODEOWNERS示例没有真实维护者，不自动启用。单人阶段自检和分轮复查如实记录，不伪称他人批准。
